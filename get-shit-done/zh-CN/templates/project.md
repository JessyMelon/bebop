# PROJECT.md 模板

用于 `.planning/PROJECT.md` 的模板 - 项目的持续更新上下文文档。

<template>

```markdown
# [Project Name]

## 项目是什么

[当前准确描述 — 2-3 句话。这个产品做什么，面向谁？
使用用户的语言和表述方式。当现实偏离此描述时及时更新。]

## 核心价值

[唯一最重要的事情。即使其他都失败了，这一点也必须成立。
用一句话说明在出现取舍时如何驱动优先级。]

## 需求

### 已验证

<!-- 已发布且已确认有价值。 -->

(尚无 — 发布后验证)

### 当前进行中

<!-- 当前范围。正在朝这些目标构建。 -->

- [ ] [Requirement 1]
- [ ] [Requirement 2]
- [ ] [Requirement 3]

### 范围外

<!-- 明确边界。包含原因以防止后续重新加入。 -->

- [Exclusion 1] — [why]
- [Exclusion 2] — [why]

## 背景

[影响实现的背景信息：
- 技术环境或生态
- 相关既有工作或经验
- 用户研究或反馈主题
- 需要解决的已知问题]

## 约束

- **[Type]**: [What] — [Why]
- **[Type]**: [What] — [Why]

常见类型：Tech stack、Timeline、Budget、Dependencies、Compatibility、Performance、Security

## 关键决策

<!-- 约束未来工作的决策。在整个项目生命周期中持续补充。 -->

| 决策 | 理由 | 结果 |
|----------|-----------|---------|
| [Choice] | [Why] | [✓ Good / ⚠️ Revisit / — Pending] |

---
*最后更新：[date]，更新时机：[trigger]*
```

</template>

<guidelines>

**项目是什么：**
- 当前准确的产品描述
- 用 2-3 句话说明它做什么、面向谁
- 使用用户的措辞和表述方式
- 当产品演变超出此描述时更新

**核心价值：**
- 唯一最重要的事情
- 其他都可以失败；这一点不行
- 在出现取舍时驱动优先级
- 很少变化；如果变化，通常意味着重大转向

**需求 — 已验证：**
- 已发布并证明有价值的需求
- 格式：`- ✓ [Requirement] — [version/phase]`
- 这些需求应视为锁定 - 修改它们需要明确讨论

**需求 — 当前进行中：**
- 当前正在构建的范围
- 在发布并验证前，这些都只是假设
- 发布后移到已验证，若被否定则移到范围外

**需求 — 范围外：**
- 明确说明我们不做什么
- 始终附带原因（防止之后重新加入）
- 包括：考虑后拒绝、延期到未来、明确排除

**背景：**
- 为实现决策提供依据的背景
- 技术环境、既有工作、用户反馈
- 需要处理的已知问题或技术债
- 出现新上下文时更新

**约束：**
- 实现选择上的硬限制
- 技术栈、时间线、预算、兼容性、依赖
- 说明“为什么” - 没有理由的约束会被质疑

**关键决策：**
- 影响未来工作的重大选择
- 在项目推进过程中持续记录决策
- 已知时记录结果：
  - ✓ Good — 决策被证明正确
  - ⚠️ Revisit — 决策可能需要重新考虑
  - — Pending — 目前还太早，无法评估

**最后更新：**
- 始终记录文档更新时间和触发原因
- 格式：`after Phase 2` 或 `after v1.0 milestone`
- 这会触发对内容是否仍然准确的复查

</guidelines>

<evolution>

PROJECT.md 会在整个项目生命周期中持续演化。
这些规则会嵌入生成的 PROJECT.md（## Evolution 部分）
并由 workflows/transition.md 和 workflows/complete-milestone.md 实现。

**每次阶段切换后：**
1. 需求失效了？→ 移到范围外并附上原因
2. 需求已验证？→ 移到已验证并附阶段引用
3. 出现新需求？→ 加到当前进行中
4. 有决策需要记录？→ 加到 Key Decisions
5. “项目是什么”还准确吗？→ 若已偏离则更新

**每个里程碑之后：**
1. 全面复查所有部分
2. 检查核心价值 - 它仍然是正确的优先级吗？
3. 审核范围外内容 - 原因仍然成立吗？
4. 用当前状态更新 Context（用户、反馈、指标）

</evolution>

<brownfield>

对于现有代码库：

1. 先通过 `/gsd-map-codebase` **映射代码库**

2. 从现有代码中**推断已验证需求**：
   - 代码库实际上在做什么？
   - 已经建立了哪些模式？
   - 哪些部分显然在工作且被依赖？

3. 从用户处**收集当前进行中的需求**：
   - 展示推断出的当前状态
   - 询问他们接下来想构建什么

4. **初始化：**
   - 已验证 = 从现有代码推断
   - 当前进行中 = 用户此次工作的目标
   - 范围外 = 用户指定的边界
   - 背景 = 包含当前代码库状态

</brownfield>

<state_reference>

STATE.md 会引用 PROJECT.md：

```markdown
## 项目引用

参见：.planning/PROJECT.md（更新于 [date]）

**核心价值：** [来自核心价值部分的一句话]
**当前焦点：** [当前阶段名称]
```

这样可确保 Claude 读取当前的 PROJECT.md 上下文。

</state_reference>

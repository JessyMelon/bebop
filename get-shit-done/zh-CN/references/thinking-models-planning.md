# 思维模型：规划类

面向 **planner** 和 **roadmapper** agent 的结构化推理模型。在创建计划过程中的决策点使用，而不是持续使用。每个模型都针对一种有文档记录的特定失败模式。

来源：基于 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ models）整理。筛选标准是与 GSD 规划工作流直接相关。

## 冲突处理

Pre-Mortem 和 Constraint Analysis 都分析风险，但粒度不同。先做 Constraint Analysis（识别最难的约束），再做 Pre-Mortem（围绕该约束和计划其余部分枚举失败模式）。

## 1. 事前验尸分析

**用于防止：** 过于乐观的计划拆解，忽略失败模式。

在最终敲定这个计划之前，先假设它已经失败。列出最可能导致失败的 3 个原因，例如缺失依赖、拆解错误、低估复杂度，并为每个失败原因补上能尽早发现问题的缓解步骤或验收标准。

## 2. MECE 拆解

**用于防止：** 任务重叠（导致 merge conflict）或任务有缺口（遗漏需求）。

在**需求层面**验证这份任务拆解是否满足 MECE：(1) 列出 phase goal 的每一项需求，(2) 确认每项需求都且只映射到一个任务的 `<done>`，(3) 如果两个任务修改同一文件，确认它们修改的是**不同**部分或服务于**不同**需求，(4) 标记任何未被任务覆盖的需求。

## 3. 约束分析

**用于防止：** 把最难的约束拖到最后一个任务，导致后期失败。

识别这个 phase 中最难的单一约束，也就是一旦失败，其他工作都失去意义的那个点。把它排在 Task 1 或 2，而不是最后。如果该约束涉及外部 API 或陌生库，就在主实现前增加一个 spike/proof-of-concept 任务。

## 4. 可逆性测试

**用于防止：** 对廉价决策过度分析，对高成本决策分析不足。

对计划中的每个重要决策，分类为 REVERSIBLE（之后可低成本修改）或 IRREVERSIBLE（之后修改需要迁移、破坏性变更或显著返工）。将分析时间与其不可逆程度成比例。对于不可逆决策，要在计划中记录理由。

## 5. 知识诅咒对冲

**用于防止：** 由于指令被压缩，导致 plan 到 executor 之间产生歧义。

对每个 `<action>` 步骤，把自己当作**从未**见过这个代码库的人重新阅读。每个名词是否都没有歧义（哪个文件？哪个函数？哪个 endpoint？）？每个动词是否都足够具体（在哪加？怎么改？）？如果一步能被解释成两种方式，就重写它。每个 action step 都要包含文件路径、函数名和预期行为。

## 6. 基准率忽视对冲

**用于防止：** planner 忽略低置信度研究结论中的保留项。

在完成计划之前，读取 SUMMARY.md 中**所有** `[NEEDS DECISION]` 项和 LOW-confidence 建议。对每一项，要么 (a) 创建一个 `checkpoint:decision` 任务来解决它，要么 (b) 在计划的 deviation notes 中说明为何该风险可以接受。静默接受 LOW-confidence 项，最终会变成未记录的技术债。

## 缺口闭合模式：根因检查

**仅适用于：** Planner 进入 gap closure mode（由 VERIFICATION.md 中的 `gaps_found` 触发）。

在编写修复计划之前，先做一轮简单的“为什么”：这个 gap 为什么会发生？是计划缺陷（任务本身错了）、执行遗漏（任务对了但实现错了），还是假设变化（环境/依赖发生漂移）？修复计划必须针对根因类别，而不只是针对表面症状。

---

## 何时不必启用这些模型

在以下情况下，跳过结构化推理模型：

- **单任务计划** -- 如果一个 phase 只有一个明确需求和一个显而易见的任务，就不要做 Pre-Mortem 或 MECE 分析，直接写任务。
- **研究已经充分的 phase** -- 如果 RESEARCH.md 对每个决策都给出了 HIGH-confidence 建议，且没有 `[NEEDS DECISION]` 项，就跳过 Base Rate Neglect Counter。研究已经消除了不确定性。
- **修订迭代** -- 根据 checker 反馈修订计划时，只聚焦修复被指出的问题。不要在每次修订时重新跑完整模型集，只应用与该具体问题相关的模型（例如 checker 发现覆盖缺口时才用 MECE）。
- **模板化计划** -- 配置变更、版本升级、文档更新。这些任务的失败模式不值得做 pre-mortem 分析。

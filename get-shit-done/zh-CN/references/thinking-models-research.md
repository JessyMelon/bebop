# 思维模型：研究类

面向 **researcher** 和 **synthesizer** agent 的结构化推理模型。在研究与综合过程中的决策点使用，而不是持续使用。每个模型都针对一种有文档记录的特定失败模式。

来源：基于 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ models）整理。筛选标准是与 GSD research 工作流直接相关。

## 冲突处理

**First Principles 和 Steel Man 都会扩大分析范围**，先运行 First Principles（拆解问题），再运行 Steel Man（强化备选方案）。不要同时运行。

## 1. 第一性原理思维

**用于防止：** 接受表层解释，而不拆解到底层组成部分。

在接受任何技术推荐或架构模式之前，把它拆解为最基本的约束：它解决什么问题？哪些需求不可谈判？物理/逻辑边界是什么？应当从这些约束**向上**构建建议，而不是从约定俗成的做法**向下**套用。如果你无法从第一性原理解释某个建议为什么正确，无论来源数量多少，都应将其标记为 `[LOW]`。

## 2. 辛普森悖论意识

**用于防止：** synthesizer 汇总相互冲突的研究结果时，不检查是否存在混杂拆分维度。

当你合并多份研究文档且它们给出矛盾结论时，检查这种矛盾在按隐藏变量拆分后是否消失：框架版本、部署目标、项目规模或使用场景类别。一个库整体 benchmark 更快，但对**你的**特定负载可能更慢。在用多数票解决矛盾前，先问：“是否存在某个子群拆分，能解释为什么这两个发现各自在自己的上下文里都成立？”

## 3. 幸存者偏差

**用于防止：** 只找到成功案例，却忽略失败案例和被放弃的方案。

在为推荐方案收集支持证据之后，要主动搜索那些**放弃**该方案的项目。查看 GitHub issues 中的 “migrated away from”、“replaced X with” 或 “problems with X at scale”。一种技术即使有 10 个成功案例和 100 个沉默失败，在你检查“墓地”之前看起来都很不错。要把负面证据（迁移离开案例、弃用通知、未解决 issue）看得比正面证据**更重**，因为失败通常不会被充分报告。

## 4. 确认偏误对冲

**用于防止：** 只搜索支持初始假设的证据，而忽略反证。

在形成初步建议后，用完整的一轮研究去搜索**反对**它的证据。使用诸如 “{technology} problems”、“{technology} alternatives”、“why not {technology}”、“{technology} vs {competitor}” 的搜索词。对每条找到的反证，要么 (a) 用更高置信度来源反驳它，要么 (b) 把它作为保留项加入你的建议。如果你完全找不到对该建议的任何批评，那说明你的搜索范围太窄了，应当扩大范围。

## 5. 最强化论证

**用于防止：** 没有用最强形式理解备选方案，就直接否定它。

在反对某个替代技术或方案之前，先构建它**最强**的论证。一个强烈支持者会怎么说？它在哪些 use case 中比你的推荐更合适？哪些权衡对它有利？把经过 steel-man 处理的备选方案与推荐方案一起呈现，并做诚实比较。如果这个 steel-man 后的备选方案仍有竞争力，就把决策标记为 `[NEEDS DECISION]`，而不是单方面给出推荐。

---

## 何时不必启用这些模型

在以下情况下，跳过结构化推理模型：

- **CONTEXT.md 中已锁定的决策** -- 如果用户已经决定“使用库 X”，就不要对替代方案做 Steel Man 分析，也不要对这个选择做 First Principles 拆解。应研究如何把 X 用好，而不是研究 X 是否正确。
- **标准技术栈查阅** -- 如果你只是查看某个知名库的最新版本，或阅读其 API 文档，就不要调用 Survivorship Bias 或 Confirmation Bias Counter。这些模型用于评估有争议的建议，而不是做事实查询。
- **单技术 phase** -- 如果这个 phase 只涉及一种技术，且没有备选方案需要评估（例如“添加 ESLint 规则 X”），就跳过比较型模型（Steel Man、Confirmation Bias Counter），直接研究实现方式。
- **仅代码库内部研究** -- 如果研究内容纯粹是内部的（理解现有代码模式、查找某个函数在哪里被调用），结构化推理模型没有价值。直接 grep 并读代码。

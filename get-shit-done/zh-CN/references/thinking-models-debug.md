# 思维模型：调试类

面向 **debugger** agent 的结构化推理模型。在调查过程中的决策点使用，而不是持续使用。每个模型都针对一种有文档记录的特定失败模式。

来源：基于 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ models）整理。筛选标准是与 GSD 调试工作流直接相关。

## 冲突处理

**Fault Tree 和 Hypothesis-Driven 是顺序关系：** 先做 Fault Tree（生成可能原因树），再做 Hypothesis-Driven（系统地测试每个分支）。Fault Tree 提供路线图；Hypothesis-Driven 提供遍历它的纪律。

## 1. 故障树分析

**用于防止：** 未系统梳理失败路径就跳到结论。

在测试任何假设之前，先构建 fault tree：以观察到的症状为根节点，然后在每一层分解所有可能原因（硬件、软件、配置、数据、环境）。使用 AND/OR gate，有些故障需要多个条件同时成立（AND），有些则有独立触发条件（OR）。这棵树就是你的调查路线图。按可能性和可测试性为分支排序，但不要仅因看起来不太可能就剪掉分支，容易测试的低概率原因也应尽早验证。

## 2. 假设驱动调查

**用于防止：** 随机改动然后碰运气，即“shotgun debugging”反模式。

对 fault tree 中的每个假设，都遵循严格流程：PREDICT（“如果假设 H 正确，那么测试 T 应产生结果 R”）、TEST（只执行一个测试）、OBSERVE（记录实际结果）、CONCLUDE（匹配 = SUPPORTED，失败 = ELIMINATED，意外 = 新证据）。绝不要跳过 PREDICT 步骤，没有预测，就无法区分有意义的结果和噪声。每次测试也绝不要同时改变多个变量，如果改了两处 bug 消失了，你就不知道究竟是哪一处修复了问题。

## 3. 奥卡姆剃刀

**用于防止：** 在尚未排除简单解释前，追逐复杂解释。

在调查复杂的多组件交互 bug、竞争条件或框架级问题之前，先验证简单解释：变量名拼写错误、文件路径错误、缺失 import、配置值错误、缓存陈旧、环境变量错误。这些“无聊”的原因占了绝大多数 bug。只有在简单原因被排除后，才升级到复杂假设。如果你当前的假设要求 3 个以上问题同时发生，先退一步，寻找单点故障。

## 4. 反事实思维

**用于防止：** 没有通过追问“如果只改这一处会怎样”来隔离因果关系。

当你对根因有一个假设时，构造一个反事实：“如果我**只**改这一个变量/配置/代码行，bug 应该消失（或出现）。”执行这个反事实测试。如果在精准改动后 bug 仍然存在，说明你的假设是错的，原因在别处。如果 bug 消失了，你就获得了强因果证据。这比相关性判断（“bug 在部署 X 后出现”）更有力，因为它测试的是机制，不只是时间线。

---

## 何时不必启用这些模型

在以下情况下，跳过结构化推理模型：

- **明显的单一原因 bug** -- 如果错误信息已经准确给出文件、行号和原因（例如 `TypeError: Cannot read property 'x' of undefined at foo.js:42`），就直接修复。不要为一个带堆栈的空引用问题去画 fault tree。
- **复现已知修复** -- 如果你已经从之前的调查中知道根因，或用户已明确告诉你哪里错了，就跳过假设驱动调查，直接修复。
- **拼写错误、缺失 import、路径错误** -- 如果 Occam's Razor 立刻就能解决，直接应用修复，不必调用完整模型。模型是给简单检查失败时用的，不是给简单检查设门槛的。
- **阅读错误日志** -- 读取并理解错误输出本来就是正常调试，不算“决策点”。只有当你面对多个合理假设并需要决定先测哪一个时，才调用模型。

# 思维模型：执行类

面向 **executor** agent 的结构化推理模型。在任务执行过程中的决策点使用，而不是持续使用。每个模型都针对一种有文档记录的特定失败模式。

来源：基于 [thinking-partner](https://github.com/mattnowdev/thinking-partner) 模型目录（150+ models）整理。筛选标准是与 GSD 执行工作流直接相关。

## 冲突处理

**Forcing Function 和 First Principles 都会推动“现在就做”。** 先运行 First Principles（理解约束），再运行 Forcing Function（创建机制）。两者是顺序关系，不是竞争关系。

## 1. 关注圈与控制圈

**用于防止：** 执行器试图修复超出自身范围的问题，例如上游 bug、无关技术债、基础设施问题。

在修改任何未明确列在计划 `<files>` 部分中的代码之前，先问：这属于我的 Circle of Control（计划范围内）还是 Circle of Concern（我注意到但不该修）？如果属于 Circle of Concern：将其记录为 deviation note 或 deferred item，**不要修复**。执行器的工作是实现计划要求，而不是顺手改善整个代码库。“既然都来了顺便修一下”造成的范围蔓延，是执行器超时的首要原因。

## 2. 强制函数

**用于防止：** 把艰难决策拖到运行时，而不是在构建期解决。

当你遇到模糊需求或不清晰的集成点时，创建一个 forcing function，让决策**现在**显式化，而不是藏在 TODO 或运行时检查后面。示例：使用 TypeScript `never` 类型强制 exhaustive switch、为必填配置增加构建期断言、创建一个迫使调用方处理错误情况的接口。如果某个决策确实无法在构建期做出，就把它记录为 `checkpoint:decision` deviation，不要静默延期。

## 3. 第一性原理思维

**用于防止：** 不理解适配性，就照搬现有代码模式。

在从别的文件或 phase 复制模式之前，先拆解它**为什么**存在：它满足了什么约束？你的当前任务是否有相同约束？如果没有，这个模式可能只是 cargo cult。应从任务的真实需求出发构建实现，而不是从最近的现成示例出发。拿不准时，以计划中的 `<action>` 步骤定义要构建什么，实现应从这些步骤推导，而不是从邻近代码推导。

## 4. 奥卡姆剃刀

**用于防止：** 用不必要的抽象、泛型或面向未来扩展把简单任务过度工程化。

在增加抽象层、泛型类型参数、工厂模式或配置选项之前，先问：计划**是否要求**这种灵活性？如果计划说“创建一个做 X 的函数”，那就创建一个做 X 的函数，不要做成一个理论上可以通过 Y 再通过 Z 来做 X 的可配置、可扩展、可插拔框架。满足计划 `<done>` 条件的最简单实现就是正确实现。只有在计划明确要求时才增加复杂度。

## 5. 切斯特顿围栏

**用于防止：** 不理解原有意图就移除或修改现有代码。

在移除、替换或大幅修改计划会触及的现有代码之前，先弄清楚它**为什么**会这样写。检查：引入它的 git blame 提交、解释原因的注释、覆盖它的测试用例、创建它的 PLAN.md 或 SUMMARY.md。如果目的不清楚，就保留它，并加一条说明不确定性的注释；**不要**移除你不理解用途的代码。即便计划明确要求删除，也仍应在 deviation notes 中说明它原本做了什么。

## 何时不必启用这些模型

在以下情况下，跳过结构化推理模型：

- **直接明了的任务动作** -- 如果计划写着“创建文件 X，内容为 Y”，且动作没有歧义，就直接执行。不要为了分析“为什么要创建计划要求的文件”而调用 First Principles。
- **遵循既有项目模式** -- 如果代码库已有清晰一致的模式（例如每个 route handler 结构都相同），计划也只是让你再加一个，那就照着做。Chesterton's Fence 适用于移除模式，不适用于遵循模式。
- **琐碎文件编辑** -- 添加 import、修复 typo、更新版本号。这些都是机械性变更，不涉及设计决策。
- **运行 verify 命令** -- 执行计划里的 `<verify>` 步骤是程序性工作。只有 verify 失败且你需要决定如何响应时，才调用模型。

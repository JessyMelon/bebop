# GSD SDK query 迁移说明（摘要）

适合复制到 Discord 和 GitHub 评论中。

---

**@gsd-build/sdk** 用一个有类型、经过测试、基于注册表的查询系统和 **`gsd-sdk query`**，替换了无类型、单体式的 `gsd-tools.cjs` 子进程。这样 GSD 就能获得结构化结果、分类错误（带 `ErrorClassification` 的 `GSDError`），以及与旧 CLI 的黄金样本一致性验证。框架因此拥有了一个稳定契约，而不再依赖一个脆弱、庞大的 CLI，让每个工作流都必须手动启动并解析它的输出。

**用户可以期待什么**

- 仍然是他们已经在用的同一套 GSD 命令和工作流。
- 运行更快一些（链式工具调用时减少了 Node 启动开销）。
- 工作流中途出现莫名其妙失败的情况更少，升级也更安全，因为行为有测试覆盖，并且只依赖一个稳定契约。
- 更强的可预测性：输出和失败模式都更一致、更明确。

**成本和 token**

这个 SDK 不会自动减少每次模型调用的 LLM token。收益是间接出现的：更少的歧义工具结果、更少的重试或恢复循环，通常会降低真实会话成本和整体耗时。

**代理：过去 vs 现在**

代理始终遵循工作流指令。真正改进的是这些步骤运行其上的表面层。以前，工作流实际上是让系统去 shell 调用 `gsd-tools.cjs`，再用脆弱的假设去解释 stdout 或 JSON。现在，它们指向 **`gsd-sdk query`** 和返回提示词期望结构的类型化处理程序；当某些内容必须停止或修复时，错误原因也更清晰。这样一来，指令遵循在端到端都更稳定，减少了错误解析或静默输出漂移带来的反复折腾。
